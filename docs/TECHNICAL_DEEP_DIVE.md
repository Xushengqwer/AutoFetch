# 《三国志·战略版》战报收集系统 - 深度技术剖析与踩坑指南

本文档全面记录了项目的底层技术验证、逆向分析结论以及自动化研发过程中遭遇的全部核心陷阱与终极解决方案。

---

## 1. 客户端技术底座分析

### 1.1 游戏引擎：Ejoy2D (灵犀互娱自研引擎)
* **执行主程序**：`S3Client.exe`（32/64位 Windows 原生可执行文件）
* **窗口类名**：`EJOY2DX`
* **图形渲染**：Direct3D / OpenGL 纯 GPU 渲染画布（Swapchain）。
* **操作系统视图**：
  在 Windows OS 视角下，该游戏**仅有一个顶层窗口句柄（HWND），其内部的 Win32 子控件树数量为 0**。
  游戏内所有战报文本、武将头像、战功统计、返回按钮，本质上均是在 GPU 帧缓冲区直接绘制的像素贴图（Texture）。
  经二进制排查，`S3Client.exe` **未链接 `UIAutomationCore.dll` 或 `oleacc.dll`**，因此系统的无障碍辅助接口（UI Automation / 元素树查找）完全无法穿透游戏内部。

## 2. 方案可行性终审与证伪报告

针对探索过程中提出的各种替代方案，我们通过真实代码与运行环境进行了严格的逆向测试：

### 2.1 方案 A：监控本地缓存文件（极具性价比的“捷径”探索）——【实测证伪：不可行】
* **假说**：玩家点开战报时，客户端会将战报数据缓存在本地磁盘（如 AppData\LocalLow、安装目录 `.db` 或 `.json` 文件），只需监听文件变动即可零 OCR 提取。
* **实测过程**：
  在游戏打开战报并运行期间，编写脚本监控全盘及 `C:\Program Files\sgzzlb\data\` 下所有文件的实时修改时间（mtime）。
* **实测结论**：
  1. 游戏点开战报时，磁盘上**唯一被写入的文件是 `data\Library\Caches\tex_cache\*.win`**（GPU 纹理立绘贴图缓存）；
  2. 游戏目录下**完全不存在战报数据相关的 SQLite 数据库（.db）、JSON 或明文数据包**；
  3. `AppData\LocalLow` 目录不存在三战的任何数据（该目录为 Unity 引擎专属）；
  4. **根本原理**：三战是基于手游架构开发的 SLG，为保护移动端闪存（Flash）寿命并防止小文件 I/O 卡顿，所有战报数据经由 TCP 加密流拉取后，**全部直接存放于客户端内存堆栈（RAM）的 Lua Table 中**，退出游戏内存即释放，根本不产生本地文件落盘。

### 2.2 方案 B：内存读写 (ReadProcessMemory / Hook) 与网络抓包 (MITM)——【绝对禁止：封号红线】
* 三战客户端搭载了**阿里安全 ACE 反作弊驱动**，具备高度敏感的内存钩子检测与进程完整性校验；
* 尝试注入 DLL 或使用 `ReadProcessMemory` 读取 Lua 数据，会被当场拦截并下发 30 天起步的封号处罚；
* 专有 TCP 通信协议经过非对称加密和动态加盐，自建代理劫持网络同样属于外挂级违规行为。

### 2.3 唯一合法通路：非侵入式展示层计算机视觉 (OCR + CV)
* 只读取显卡输出给人眼看的屏幕画面，只模拟人手点击鼠标，**100% 遵守游戏用户协议，绝对零封号风险**。

## 3. 研发过程核心踩坑实录与终极修复

### 陷阱 1：右上角金色【返回】按键偏差 21 像素
* **表象**：脚本截完图后退出失败，多次尝试后画面误触进入大地图。
* **根因**：旧代码将返回按钮写死为高度的 `7.5%`（720p 下 Y=54）。然而真机上真正的金色【返回】按钮正中心在 `Y=33`（高度的 `4.6%`），鼠标整整点低了 21 像素，点在空白处未能退回列表！留在详情页的代码把“下一条战报”点在了详情页的“战斗地点”超链接上，导致镜头飞向大地图。
* **修复方案**：
  采用 Windows 原生高精度 OCR 动态定位 `返回` 文字框中心点（1080p 下直接定位到 `X=1815, Y=30`，720p 定位到 `X=1195, Y=33`），误差归零。

### 陷阱 2：卡片正中间的蓝色坐标超链接（地名避障）
* **表象**：点击展开卡片时，经常莫名其妙跳出战报页面，直接跳转到大地图上的资源地（如“4级木材”、“长社大营”）。
* **根因**：战报卡片正中间（`X = 0.50 * W`）恰好是战报发生地的坐标超链接（例如 `长社大营(1318,913)`）。在正中心点击等同于点击了坐标传送门。
* **修复方案**：
  所有战报点击热区向左偏移至**左侧友军武将战旗安全区（`X = 0.25 * W` 或 `X = 0.35 * W`）**，该区域只有武将名字和兵力，百分之百没有地名链接。

### 陷阱 3：Windows UIPI (用户界面特权隔离) 吞噬鼠标点击
* **表象**：后台调试脚本调用 `pyautogui.click()`，鼠标在屏幕上移动，但游戏完全没有任何反应。
* **根因**：`S3Client.exe` 启动时通过官方启动器申请了 Windows 管理员权限（UAC Elevated）。根据 Windows 系统的安全机制（UIPI），普通权限的进程向管理员权限的窗口发送合成鼠标键盘消息时，会被内核静默丢弃！
* **修复方案**：
  在 `main_gui.py` 启动入口加入 `check_and_elevate()` 自动提权，检测到非管理员时自动弹出 UAC 对话框以管理员身份重启进程。

### 陷阱 4：连战折叠条（鏖战多穿）的原生两步交互与死循环
* **表象**：连续采集 4~5 次，生成的全部是同一张单场战报，随后截取到收集器 UI。
* **根因**：
  1. 在游戏原生交互中，单点连战组的某一行，**只会在下方展开该场的军队卡片，并不会直接弹进【战斗回放】全屏详情页**；
  2. 旧代码在连战分支里写死了 `target = collapsed_rows[0]`，点完第一场返回列表后，由于没有推进序号，下一轮循环又去点第 0 项；
  3. 没弹全屏时又触发了备用逻辑，导致把屏幕最下方的单场卡片反复采集了 4 遍。
* **修复方案**：
  采用两步法确定性流水线：精准点击序号行 ➔ 确认下方展开 ➔ 点击展开卡片进详情 ➔ 闭环退出 ➔ 严格推进到第 2 场、第 3 场。

### 陷阱 5：多显示器与自定义窗口缩放漂移 (1501×844)
* **表象**：用户换到 2K 显示器或最大化窗口后，之前调好的坐标全部点歪。
* **根因**：用户的显示器是 2560×1440，游戏窗口被拉伸为自定义的 1501×844 自由尺寸，任何写死像素的算法均告失效。
* **修复方案**：
  1. 调用 `SetProcessDpiAwareness(2)` 彻底规避 Windows DPI 缩放换算失真；
  2. 采用【两步法】中的第一步——`calibrate.py` 视觉瞄准靶向脚本，在真实客户区截面上实时绘制 8 个红圈十字靶心，肉眼和 AI 双重校准确认无误后再执行动作。
